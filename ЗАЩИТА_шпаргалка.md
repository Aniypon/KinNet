# KinNet — шпаргалка для защиты

> Цель файла: за 5 минут понять, **что это, на чём построено и как работает**, чтобы ответить на любой общий вопрос комиссии.

---

## 1. Что это (одна фраза)

**KinNet** — семейная социальная сеть и органайзер: в одном пространстве семейное древо, общий календарь, задачи, кулинарная книга со списком покупок, дашборд здоровья, бюджет, опросы, капсулы времени и система достижений. Веб-приложение (PWA), язык интерфейса — русский.

---

## 2. На чём построено (стек) — главный технический вопрос

| Слой | Технология | Зачем |
|---|---|---|
| **Backend** | Django 5 (Python) | Монолит, серверный рендеринг шаблонов |
| **REST API** | Django Ninja + Pydantic | Типизированный API, авто-документация на `/api/docs` |
| **БД** | PostgreSQL (прод) / SQLite (локально) | Реляционная, через `dj-database-url` |
| **Кеш + realtime** | Redis | Кеш, сессии, pub/sub для уведомлений |
| **Фоновые задачи** | Celery + celery-beat | Отложенные/периодические задачи (напоминания) |
| **Frontend** | Django-шаблоны + Vite + Tailwind + HTMX + Alpine.js | Без отдельного SPA: HTMX даёт «живость» без тяжёлого фронта |
| **Realtime** | Server-Sent Events (SSE) + Redis pub/sub | Уведомления в реальном времени |
| **PWA** | manifest + service worker + offline-страница | Установка на телефон, офлайн |
| **Деплой** | Docker Compose + nginx | Весь стек одной командой |

**Архитектурное решение #1:** монолит на Django с серверным рендерингом, а не SPA. Меньше сложности, быстрее разработка, SEO/доступность из коробки. «Живость» добавляет HTMX (частичные обновления) + Alpine.js (мелкая интерактивность).

## 3. Как устроен код (архитектура)

Два слоя:
- **`core/`** — ядро домена: `Family`, `FamilyMember`, `FamilyMembership`, `Event`, `Task`, `Goal`, `Message`, `UserProfile`, приглашения, фото, теги.
- **`apps/`** — продуктовые модули, каждый смонтирован под своим URL-префиксом: `api`, `cookbook`, `health`, `budget`, `polls`, `calendar_sync`, `gamification`, `timecapsule`, `notifications`.

**Ключевая идея — «активная семья»:** один пользователь может состоять в нескольких семьях. Текущая семья определяется context-processor'ом (`?family=` → POST → сессия → первая доступная) и инжектится в каждый шаблон. Переключение — `<select>` в шапке.

**Доступ к данным:** пользователь видит только данные своих семей (через `FamilyMembership` или `created_by`). Роли проверяются декоратором `require_family(roles=...)` и `has_role`.

## 4. Как работают уведомления (частый вопрос про realtime)

- Событие (`post_save` на Event/Task/Goal/Message/Badge) ловит Django-сигнал.
- `notify()` пишет запись в БД **и** публикует payload в Redis pub/sub-канал пользователя.
- View `/notifications/stream/` подписан на канал и стримит через **SSE** (`EventSource` на фронте) — toast + счётчик непрочитанных.
- **Почему SSE, а не WebSocket:** канал односторонний (сервер → клиент), авто-reconnect из коробки, проще, не нужен отдельный WS-сервер.
- **Fallback:** нет Redis → polling раз в 60 сек, записи в БД остаются.

## 5. Безопасность (если спросят)

- Аутентификация — сессии Django (cookie) + CSRF-токены.
- API авторизуется той же сессионной cookie (`django_auth`).
- Валидаторы паролей Django, сброс пароля — по заявке через владельца семьи.
- Изоляция данных по семьям на уровне запросов (нельзя увидеть чужую семью).
- В проде: `DEBUG=0`, `SECRET_KEY` из env, `ALLOWED_HOSTS`, nginx перед Django.

## 7. Деплой (если спросят про инфраструктуру)

`docker compose up -d --build` поднимает 6 контейнеров: **web** (gunicorn), **worker** (Celery), **beat** (расписания), **db** (Postgres), **redis**, **nginx** (отдаёт статику/медиа, проксирует на web). Прод работает на VDS.

**Зачем nginx перед Django:** Django не должен сам раздавать статику и держать публичный порт. Nginx — реверс-прокси: отдаёт статику/медиа напрямую, буферизует соединения, точка для TLS/HTTPS.

## 8. Что отвечать на типичные вопросы

- **«Почему Django?»** — батарейки в комплекте (ORM, админка, auth, миграции), быстрая разработка монолита, серверный рендеринг.
- **«Почему не SPA/React?»** — продукт контентный, не нужен тяжёлый клиент; HTMX+Alpine дают интерактивность дешевле.
- **«Как масштабируется?»** — stateless web-контейнеры за nginx, сессии/кеш в Redis, фон в Celery — можно поднять несколько реплик web/worker.
- **«Почему SSE а не WebSocket?»** — односторонний канал, авто-reconnect, проще инфраструктура.
- **«Тесты есть?»** — да, 82 теста, 64%, CI + ruff.
